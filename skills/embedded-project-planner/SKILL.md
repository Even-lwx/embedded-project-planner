# 嵌入式项目规划器

## 输入与边界

要求用户提供项目根路径和最终目标功能。信息不足时，先从项目中查证；只有无法从文件确定且会改变方案的问题才询问用户。

首次调用必须处于**规划阶段**：只允许读取、搜索和执行不会改动项目源文件的检查，禁止创建、编辑、删除、格式化或生成项目文件。构建或检查若可能改写受版本控制的文件，也不要运行。

只有用户在看到当前计划后，明确表达“按该计划实施”“开始修改”或同等含义，才进入**实施阶段**。初次请求中的“开发”“实现”等目标描述不构成实施授权。无论处于哪个阶段，`pcb/` 和 `doc/` 始终只读；未经单独要求不要创建 Git 提交。

## 调查顺序

严格按照 `pcb/`、`doc/`、`code/` 的顺序调查。后一步可以补充前一步，但不能跳过前一步直接假设硬件条件。

### 1. 验证项目结构

- 解析并确认根路径，查找大小写等价的 `pcb/`、`doc/`、`code/` 目录。
- 先列出目录和关键文件类型，避免无目的地读取整个项目。
- 若目录缺失、根路径错误或存在多个无法判断的候选工程，陈述已发现的事实并询问用户，不自行选择。

### 2. 调查 PCB

- 识别原理图、PCB Layout、BOM、网表和导出 PDF；优先使用能可靠提取连接关系的原始文件或导出物。
- 围绕目标功能确认相关芯片的完整型号、器件位号、供电、地、时钟、复位、启动配置、通信接口、中断、控制信号以及 MCU 引脚和网络连接。
- 仅当目标涉及高速信号、射频、差分、模拟、电源完整性、散热、关键走线或连接关系存在疑点时检查 Layout。
- 对关键硬件结论记录原理图文件、页名或页码、器件位号和网络名；不要把器件系列名当作完整料号。
- 对 Altium/AD 原理图（`.SchDoc`）和 PCB（`.PcbDoc`）先执行“工具发现 → 原始文件解析 → 交叉验证”的通用流程，不要因为当前环境没有 Altium GUI 就直接判定文件不可读。
- 工具发现顺序：检查本机 Altium Designer/Viewer、KiCad CLI、7-Zip/解压工具和 Python；再尝试专用解析器。可优先评估 `Altium-Schematic-Parser`（`.SchDoc` 转 JSON）和 `altium.js`（`.SchDoc` 解析/渲染）。第三方解析器必须先用当前工程文件做最小验证，不能只依据项目说明判断兼容性。
- 对 OLE/复合文档，先列出存储流并检查 `FileHeader`/记录流；若记录中存在可读的 `RECORD=...`、器件属性、引脚和网络标签，可用只读脚本提取器件清单、位号、型号、引脚和网络，再与 ECO 日志、BOM、网表或导出 PDF 交叉验证。解析脚本和中间结果放在临时目录或报告目录，不写回 `pcb/`。
- 原理图连通性解析是 PCB 调查的必经阶段：必须建立“器件引脚—导线端点—网络标签/端口—网络名”的连通图，而不只提取器件清单。至少解析并关联 `RECORD=2` 引脚、`RECORD=6` 导线、网络标签/端口记录，以及 `OwnerIndex`、`OwnerPartId`、坐标和 `UniqueID`；对每个目标器件输出引脚到网络的映射和未连接引脚清单。
- 连通图生成前不得把 MCU 引脚、充电控制脚、ADC 通道或显示控制脚写入固件配置。连通性报告必须记录解析器版本、源文件、记录定位信息和状态（已确认/推断/未连接/冲突），并用 ECO、BOM、网表、PDF 或第二解析器交叉验证关键网络。
- 解析结果必须区分：直接从原始记录读出的事实、由几何/记录关联得到的推断、尚未验证的连接。只有经过至少一种独立证据（ECO、BOM、网表、PDF 或第二解析器）确认的连接，才能进入硬件连接事实。
- 若专用解析器失败，记录失败原因并继续尝试 OLE/记录流解析；只有在这些路径都无法可靠得到连接关系时，才请求用户提供 PDF、BOM、网表、截图或其他可读导出文件。详细决策树见 `references/altium-parsing.md`。

### 3. 按需调查文档

- 依据目标功能以及 PCB 已确认的准确料号，定位 `doc/` 中相关的数据手册、参考手册、勘误、应用笔记、开发工具说明、通信协议和上下位机协议。
- 核对文档适用的芯片型号、版本和修订号，读取与目标功能有关的章节及必要上下文，而不是默认遍历所有无关文档。
- 提取寄存器及复位值、初始化前提、时序、电气或速率限制、命令字、帧格式、校验、状态与错误响应，以及工具链或配置要求。
- 关键结论必须可追溯：PDF 写明文件名和页码；文本或源码写明路径和行号；协议图表写明表号、图号或章节。页码同时存在印刷页码和 PDF 页序时，优先注明印刷页码，必要时两者都写。
- 若文档与原理图、不同版本文档或现有实现冲突，明确列出冲突双方及影响，不自行裁决无法证明的事实。

### 4. 调查现有代码

- 识别 Keil (`.uvprojx`/`.uvproj`)、IAR (`.ewp`/`.eww`)、STM32CubeMX (`.ioc`) 以及其他构建系统或 IDE 工程。
- 确认 MCU 型号、目标配置、编译器、启动文件、链接脚本、时钟和引脚配置、HAL/LL/BSP、RTOS、源码分组、现有驱动与中间件、用户库位置和测试入口。
- 阅读代表性文件以归纳命名、接口、错误处理和注释风格，并查找可以复用的抽象；不要仅凭目录名推断架构。
- 规划阶段只能描述预计新增或修改的文件、工程分组和配置，不得实际创建、编辑、格式化或执行代码生成。
- 重点记录用户自建库的目标位置：`<project>/code/code/Hardware/`，并根据工程需要规划其下的 GPIO、UART、SPI、USB、RS485、CAN 等子目录；不得仅凭接口名称假设实际外设实例、引脚或收发器。
- 底层驱动必须为每个外设初始化提供明确的成功/失败结果，并通过已确认的调试串口输出初始化结果（外设名、实例、错误码或阶段）。串口初始化应作为最早的可观测基础设施；若串口自身初始化失败，必须保留无串口条件下的错误记录或故障指示路径，不能假装已经输出。

## 不确定性处理

- 区分“已确认事实”“合理但未验证的推断”和“待用户确认项”；最终计划只能把第一类作为确定依据。
- 芯片型号、关键引脚、协议版本、目标行为或工程目标存在会改变方案的歧义时，先给出已确认事实，再提出少量具体问题。
- 阻塞项解决前可以提交调查摘要或部分计划，但不得把它称为可直接实施的最终计划。

## 计划交付格式

最终计划必须足以由另一位工程师直接实施，并按以下顺序包含：

1. **目标与约束**：目标功能、平台、工具链、范围和明确不做的事项。
2. **硬件连接事实**：相关器件、引脚、网络、电源、时钟和中断，附原理图依据。
3. **文档依据**：协议、寄存器、时序和限制条件，附可追溯引用。
4. **现有软件结构**：工程入口、关键模块、可复用接口、代码和构建约束。
5. **仓库与基础设施基线**：现有 Git 状态；是否需要初始化仓库；`.gitignore` 应覆盖的工具链、构建产物、临时文件和本地配置；基线提交边界。若已有仓库或 `.gitignore`，列出保留和调整原则。
6. **底层硬件库**：`code/code/Hardware/` 的子目录、各外设驱动的依赖、初始化接口、收发接口、超时和错误模型；明确哪些 GPIO、UART、SPI、USB、RS485、CAN 等驱动由目标硬件实际需要。
7. **模块、接口与数据流**：拟新增或修改的模块、公开接口、数据结构、调用关系和预计涉及的文件或工程分组。
8. **实施步骤**：按“Git 与 `.gitignore` 基线 → `code/code/Hardware` 底层驱动 → 上层功能 → 集成验证”的依赖顺序给出可执行步骤，并将硬件与文档依据落实到对应实现。
9. **异常处理**：超时、通信错误、无效数据、复位、并发或中断等与目标有关的失败行为。
10. **验证方案**：构建、静态检查、单元或主机测试、板级测试、仪器观测点及验收标准。
11. **风险与待确认项**：仅保留尚未解决的问题，说明每项对实施的影响。

计划中不要粘贴大段实现代码，也不要声称执行过未实际运行的测试。

## 获批后的实施阶段

1. 重新检查项目状态、相关文件和版本控制差异，避免覆盖用户在计划后产生的改动。
2. 若硬件依据、需求或代码结构发生会改变当前计划的变化，停止修改，更新计划并等待再次批准。
3. **先建立仓库基线**：如果项目根目录尚无 Git 仓库，初始化当前项目仓库；如果已有仓库，保留并检查其历史和工作区。根据实际 Keil、IAR、CubeMX、编译器、下载工具和操作系统生成或补充根目录 `.gitignore`，不得无差别覆盖用户已有规则。将项目结构、`.gitignore` 和必要的既有基线纳入一个可回滚的初始提交；若用户要求不自动提交，则停在已暂存状态并说明。
4. **再建立底层硬件库**：创建并维护 `code/code/Hardware/`，可在其中按芯片、总线或模块建立子目录。先实现 PCB 和文档证实需要的 GPIO、UART、SPI、USB、RS485、CAN 等最底层驱动，再实现上层芯片驱动和业务功能。每个驱动必须使用已确认的 MCU 外设实例、引脚复用、时钟、DMA/中断、收发器使能、终端匹配和协议限制，不得凭接口名称臆测。
5. 底层驱动的接口应与现有 HAL/LL/BSP、RTOS 和工程风格一致，明确初始化、读写、超时、错误码、并发/中断安全和资源所有权；每个 `Init` 必须返回可检查的结果，并在初始化成功或失败后通过调试串口输出统一格式的诊断信息。串口初始化失败时，使用 GPIO/LED、保留 RAM 错误码或其他已确认的故障指示，并在串口恢复后补发记录。USB、RS485、CAN 等涉及物理层器件或协议栈时，区分 MCU 外设层、收发器控制层和协议层。
6. 仅修改获批计划覆盖的 `code/` 内容，保持既有工程结构和风格；`pcb/`、`doc/` 及计划外文件不得修改。将新增源文件加入实际 IDE/构建工程，不只是在磁盘上创建文件。
7. 执行与风险相称的构建和测试，说明实际结果、未能执行的验证及剩余风险；至少验证 Git 基线可回滚、`.gitignore` 不误排除源文件、底层驱动可独立编译并能被上层功能调用。板级验收必须逐项观察每个外设的初始化成功/失败串口消息，并覆盖初始化失败、串口不可用和错误码输出路径。
